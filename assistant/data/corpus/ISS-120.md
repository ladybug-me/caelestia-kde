# ISS-120 — Feat: AI-Powered Natural Language Settings Assistant

State: OPEN · opened 2026-07-11 by dr-strange15.

This thread is OPEN: there is no resolution. It is part of the corpus because it defines what the on-device assistant itself may claim to do — no more, no less.

## Proposal (original, condensed)

I think Caelestia-kde-dots is in a unique position to make desktop customization much more approachable by allowing users to configure the shell using natural language.

Instead of manually searching through Nexus or editing configuration files, users could simply describe what they want.

Examples:

- "Make my bar thinner."
- "Move the dock to the left."
- "Increase the blur."
- "Make everything feel more compact."
- "Give the desktop a minimal look."

The assistant would interpret the request, convert it into structured configuration changes, and apply them through Caelestia's existing configuration system.

---

After looking through the project, it feels like most of the pieces already exist.

Caelestia already has:

- AI Assistant
- Ollama integration
- `ConfigObject` architecture
- Live configuration updates
- Nexus settings application

Right now these are mostly independent systems.

Connecting them together could make Caelestia one of the easiest and most intituve desktop environments on whole of linux to customize without introducing an entirely new subsystem.

---

The assistant should never modify configuration files directly.

Instead, it should only request changes through a controlled API.

The overall flow could look something like this:

```text
User
   │
   ▼
AI Assistant
   │
   ▼
Intent Parser
   │
   ▼
Structured Tool Calls
   │
   ▼
ConfigObject / …[truncated]

## Scope

Maintainer (ladybug-me, paraphrased): the AI assistant already routes shell handling through caelestia-cli but that path was not working at the time; a few tools (screenshot, get_weather, web_search, read_wbpg) worked, the rest were pending updates.
Maintainer direction (2026-09-22, paraphrased): the issue was handed over to contributor 0x0nYx, who was pointed at the shell's predefined agentic tools as the integration path.
Corpus note (curated from this thread): the on-device assistant in this repo stays on the narrow side of this proposal — it retrieves documentation and past resolutions and prints inert suggestions; it never parses natural-language requests into config writes (the settings layer is a separate module behind an explicit --apply).
Corpus note (2026-09-23 direction, open thread): the maintainer handed the issue to contributor 0x0nYx and pointed at the shell's predefined agentic tools; collaborator 0xSolanaceae wants to explore the Apertus AI model family (https://www.apertus-ai.org/) for the assistant, says assets need cutting down, and invited a PR; the model would NOT ship bundled with the shell ("it'll have to be downloaded from the ui"), and 0x0nYx expects the model asset to be "gonna publish that on GitHub instead cuz it will be ofc greater than 500mbs". Per the collaborator on 2026-09-22, implementation "has fallen to the backlog bc of all the more important features and bugfixes we need to ship first". No model choice, bundling decision, or in-shell API is settled — the thread is OPEN, with the assistant work currently backlogged behind higher-priority features and bugfixes.
