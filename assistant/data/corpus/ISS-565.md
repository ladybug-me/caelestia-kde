# ISS-565 — Dual-updater state desync

State: OPEN (as of 2026-09-26).

## Problem (condensed from the original report)

Two independent updaters deploy to the same destinations but read from
different sources of truth:

- `update.sh` (top-level, dev workflow) uses `BUNDLE_DIR` = wherever the
  script physically lives — the user's real git clone.
- `src/bin/caelestia-update` (installed to `~/.local/bin`, driven by the
  Nexus "Install Updates" button) maintains a private sparse-checkout
  clone at `~/.config/caelestia-update/repo`, does
  `git reset --hard`/`git clean -fdx` THERE, and deploys from that
  unrelated checkout.

Both paths end by writing
`~/.config/quickshell/caelestia/.current_commit` and `.update_branch`
from `git -C "$BUNDLE_DIR" rev-parse HEAD` — but `$BUNDLE_DIR` means a
different repository depending on which updater ran last.
`caelestia-check-updates` then diffs `.current_commit` against its own
bare mirror for the pending-commit badge, so alternating between the two
paths yields a commit hash that does not correspond to the user's real
clone — and the deploy from the shadow clone overwrites
`~/.config/quickshell/caelestia/*`, including discarding uncommitted
local edits in the real clone.

## What users see (the symptom this rule fingerprints)

- The Nexus Updates page reports a pending-commit count that does not
  match `git -C ~/caelestia-dots-kde log` in the real clone.
- Uncommitted local changes in the real clone disappear after using
  Nexus "Install Updates".
- `.current_commit` under `~/.config/quickshell/caelestia/` does not
  match any commit in the user's own checkout.

## Fix direction

Pick ONE updater path and stick to it; commit or stash local edits
before any updater runs; verify the real clone with
`git -C <clone> rev-parse HEAD` against
`~/.config/quickshell/caelestia/.current_commit`. The issue is open
upstream — until it lands, users alternating between `update.sh` and the
Nexus button remain exposed to the desync.
